1Executive Summary

1.1 Purpose

The Capstone RAG Chatbot is a document question-answering assistant. Users upload PDF, DOCX or TXT files (or point the loader at a web URL); the application splits each document into overlapping chunks, converts the chunks into vector embeddings, and stores them in a vector database. When a user asks a question, the most relevant chunks are retrieved and passed — together with a running summary of the conversation and the last few exchanges — to a Large Language Model (LLM), which writes a grounded answer.

The whole pipeline is assembled from LangChain building blocks. LangChain supplies the common data model (Document), provider-neutral interfaces for embeddings, vector stores, retrievers and chat models, and the LangChain Expression Language (LCEL), which the project uses to compose those parts into one runnable chain with per-session memory.

4System Architecture

4.1 Layered Architecture

The system has four layers. The presentation layer handles user interaction. The orchestration layer (the body of streamlit_app.py) calls the pipeline stages in order. The core RAG library (modules/) contains one module per stage. The provider layer holds the external AI services and vector databases, reached only through LangChain's provider-neutral interfaces.

4.3 Design Principles

🔌 Provider-neutral interfaces

Every external service is accessed through a LangChain base class (Embeddings, VectorStore, BaseChatModel, BaseRetriever). Switching from OpenAI to Gemini, or from FAISS to Pinecone, means changing a config value — the downstream code stays the same.

⚙️ Configuration-driven

config.json decides which embedding provider, vector store, retriever and LLM are used; .env holds the secrets. Factory functions (get_embedding_model, build_or_update_vectorstore, get_retriever, build_rag_chain) read the config and build the matching objects.

🔗 Composition with LCEL

The chain is built with the | operator and a RunnableParallel map rather than as one large function. Every stage is a Runnable, so it supports invoke, batch and stream, and is traced automatically in LangSmith.

🧩 One module per pipeline stage

Each pipeline stage is a separate module with a small functional API. The notebook can test each stage independently, and a new front end (for example Gradio) can reuse the whole library without changes.

👥 Session isolation

All memory stores are dictionaries keyed by a session UUID, and the session id is passed through LangChain's configurable runtime config, so several chats can run side by side without sharing context.

♻️ Incremental indexing

An existing FAISS index is loaded and new chunks are added to it (add_documents) instead of rebuilding it. For Pinecone, the index is created once and later uploads are upserted.

6.2 LangChain Concepts Explained in Project Context

6.2.1 Document — the common data unit

A Document is a small object with two fields: page_content: str and metadata: dict. All loaders in loader.py produce Documents, the splitter turns one Document into many, and the vector store keeps the metadata next to each vector so retrieved chunks can be traced back to their source file and page.

# loader.py:10 — the factory every loader goes through
def text_to_doc(text: str, source: str = "inline") -> Document:
    return Document(page_content = text, metadata = {"source": source})

6.2.2 Text Splitters — chunking for retrieval

Embedding models have input limits, and retrieval works better when each chunk covers one idea. RecursiveCharacterTextSplitter tries separators in order ["\n\n", "\n", " ", ""]: it first splits on paragraphs, splits further only where a piece is still larger than chunk_size, then merges small pieces back up to the limit while keeping chunk_overlap characters shared between neighbouring chunks.

6.2.3 Embeddings — the provider-neutral vector interface

Both OpenAIEmbeddings and GoogleGenerativeAIEmbeddings implement the Embeddings interface, which has two methods: embed_documents(list[str]) for indexing and embed_query(str) for searching. embedder.py uses this interface to measure the vector size (len(embed_documents(["Hello world!"])[0])) before creating a Pinecone index.

6.2.4 Vector Stores — FAISS and Pinecone behind one interface

⚠ Security note — allow_dangerous_deserialization=True

FAISS saves its docstore with Python pickle. LangChain requires this flag as an explicit acknowledgement, because loading a pickle file from an untrusted source can execute arbitrary code. That is acceptable here because the index is always created locally by the application. Never load an index.pkl received from someone else.

6.2.5 Retrievers — from vectors to relevant chunks

A retriever is any Runnable that takes a query string and returns List[Document]. Because it is a Runnable, it can be placed directly in an LCEL pipe (... | retriever | ...), which is how rag_chain.py uses it. The project supports two kinds:

Base retriever

vectorstore.as_retriever(search_kwargs={"k":3}). Embeds the question once and returns the 3 nearest chunks. One embedding call, no LLM call — fast and inexpensive.

MultiQueryRetriever

An LLM (temperature 0) writes several alternative phrasings of the question; each is searched separately and the results are merged and de-duplicated. Improves recall for vague or ambiguous questions, at the cost of one extra LLM call and several searches.

6.2.6 Chat Models — interchangeable LLMs

ChatOpenAI and ChatGoogleGenerativeAI both implement BaseChatModel: they take a list of messages (or a PromptValue) and return an AIMessage. build_rag_chain chooses one based on llm_provider and places it at the end of the pipe; the rest of the chain is identical for both. streaming=True is set so a later UI change can use chain.stream() to show tokens as they arrive.

6.2.7 Prompt Templates

ChatPromptTemplate.from_template(...) creates a template containing a single human message with the placeholders {system_prompt}, {memory_summary}, {recent_memory}, {context} and {question}. It is a Runnable that takes a dict with those keys — exactly what the preceding RunnableParallel returns.

6.2.9 Memory — chat history and summary memory

InMemoryChatMessageHistory is the low-level store (a list of messages). ConversationSummaryMemory is a higher-level helper from the classic langchain.memory API. It shares the same message history and uses an LLM to keep a short running summary up to date (save_context → predict_new_summary). The project adds its own rolling window of the last n turns (plain Python), giving hybrid memory: the summary keeps long-range context compact, and the window keeps the exact wording of the latest exchanges.

6.4 How the Session ID Reaches the Memory Lookups

The session id is never part of the chain's input data; it travels in LangChain's runtime config, which LCEL automatically passes down to every nested Runnable:

# 1. UI passes the id in config (streamlit_app.py:168)
rag_chain_with_memory.invoke({"question": prompt},
    config={"configurable": {"session_id": st.session_state.active_session}})

# 2. RunnableWithMessageHistory reads configurable.session_id to pick the history
# 3. It calls RunnableLambda(chain_with_summary) — which takes `config`, so LangChain passes it in
def chain_with_summary(input_data, config=None):
    response = rag_chain.invoke(input_data, config=config)   # 4. forwarded explicitly

# 5. Inside RunnableParallel, these two-parameter lambdas receive the same config
RunnableLambda(lambda x, config: get_memory_summary(config["configurable"]["session_id"]))
🦜🔗 LangChain in action — why config, not input?

Keeping the session id in configurable leaves the chain's input contract simple ({"question": ...}). Callbacks and tracing tags travel the same way, so in LangSmith every step of a session's run appears under one trace with the session metadata attached.

How add_memory_to_chain wraps the chain

def chain_with_summary(input_data, config=None):
    response  = rag_chain.invoke(input_data, config=config)      # 1. run RAG
    summary_memory.save_context({"input": q}, {"output": a})     # 2. update summary (LLM call)
    update_recent_memory(session_id, q, a, n=recent_n)           # 3. update rolling window
    new_summary = summary_memory.predict_new_summary(msgs, old) # 4. re-summarise (2nd LLM call)
    summary_memory._buffer = new_summary                          #    see finding F-05
    return response

return RunnableWithMessageHistory(
    RunnableLambda(chain_with_summary),
    get_session_history=lambda _: get_session_message_history(session_id),
    input_messages_key="question", history_messages_key="history", output_messages_key=None)
🦜🔗 LangChain in action
  • RunnableWithMessageHistory takes the human message from the question key, adds stored history under history, and records the returned AIMessage (with output_messages_key=None the whole output is treated as the message).
  • ConversationSummaryMemory is a classic (pre-LCEL) memory class used here only as a summary engine: its save_context and predict_new_summary run an internal summarisation prompt through the LLM.
  • Hybrid design: the summary provides long-range, compressed context; the rolling window keeps the exact wording of the latest turns — both are placed in the prompt on every call.

11Glossary

RAGRetrieval-Augmented Generation — retrieving relevant passages from your own data and adding them to the LLM prompt so the answer is based on that data.
LangChainOpen-source framework that provides standard interfaces and integrations for building LLM applications.
LCELLangChain Expression Language — the |-based way of combining Runnables into chains that support invoke/batch/stream and async.
RunnableLangChain's base interface for any step in a chain (prompts, models, retrievers, lambdas, parallel maps).
DocumentLangChain's text container: page_content + metadata.
ChunkA piece of a document produced by a text splitter; the unit that is embedded and retrieved.
EmbeddingA list of numbers (vector) that represents the meaning of a text; similar texts produce nearby vectors.
Vector storeA database that stores embeddings and finds the nearest ones to a query vector (FAISS, Pinecone).
RetrieverA Runnable that maps a query string to a list of relevant Documents.
Multi-Query RetrievalUsing an LLM to rewrite a question in several ways, then merging the results of each search to improve recall.
Summary memoryAn LLM-maintained short summary of a conversation, used to keep long-range context.
Rolling window memoryThe last n turns kept word for word, used for short-term context.
RunnableConfig / configurableRuntime settings passed alongside a chain's input (e.g. session_id, callbacks, tags) and passed down to every nested step.
Namespace (Pinecone)A logical partition inside a Pinecone index, used to separate data sets.
LangSmithLangChain's tracing and evaluation platform for inspecting chain runs.
